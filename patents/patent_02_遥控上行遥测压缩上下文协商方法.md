## 一、发明/实用新型名称

**名称：一种利用遥控上行链路进行卫星遥测压缩参数协商的方法与系统**

---

## 二、所属技术领域

本发明涉及卫星测控通信技术领域，特别是涉及一种利用卫星遥控（Telecommand，TC）上行链路与卫星遥测（Telemetry，TM）下行链路之间的交叉信道机制，实现星地之间遥测压缩算法参数双向协商、压缩上下文管理以及上下文失步恢复的方法与系统。

---

## 三、现有技术（背景技术）

**背景技术：**

卫星测控系统由遥控（TC）上行链路和遥测（TM）下行链路构成，两者通常在不同频段工作（上行S/X/Ka波段，下行S/X/Ka波段），形成非对称的星地交互信道。CCSDS TC空间数据链路协议（CCSDS 232.0-B）和TM空间数据链路协议（CCSDS 132.0-B）分别定义了两个方向的帧格式与规程，但两个方向的协议相互独立，没有定义跨方向的应用层协商机制。

**现有技术的主要局限性：**

**1. 缺乏遥测压缩的协商机制标准**

在卫星遥测领域，压缩参数（如压缩算法类型、量化精度、字典版本等）通常在卫星出厂前固化于星上软件，无法在轨动态更新。CCSDS体系中的数据压缩标准（CCSDS 121.0-B）仅定义算法本身，未定义星地之间的压缩参数协商机制。这导致压缩参数一旦与地面解压缩能力不匹配，将产生大规模遥测解压缩失败，且无法在轨修复。

**2. 压缩上下文的单向维护缺乏保障**

遥测数据压缩（尤其是基于上下文的增量压缩）要求星地双方维护完全一致的压缩上下文（如参数历史值缓存、分级表版本等）。然而，遥测下行链路受星地距离、遮挡、干扰等影响，存在帧丢失风险。当帧丢失发生时，地面接收端的压缩上下文可能与星上不一致，导致后续遥测帧解压缩错误，且地面无法主动触发星上重发或上下文重置。

**3. 地面移动通信参考系统的局限性**

3GPP ROHC协议（RFC 5795）中定义了压缩端与解压缩端之间的反馈机制（ROHC Feedback），解压缩端可通过反向信道向压缩端发送ACK/NACK/STATIC-NACK等反馈，触发上下文刷新。然而，ROHC反馈基于IP协议栈，反馈时延为毫秒级，而卫星遥控/遥测的单向传播时延从低轨卫星的数毫秒到地球静止轨道卫星的270毫秒不等，ROHC反馈机制无法直接应用。此外，ROHC不涉及协商阶段，其压缩配置文件（Profile）由端点预先约定，而非动态协商。

**4. 现有遥控命令体系不具备双向确认能力**

传统遥控命令按照CCSDS TC标准发送后，卫星通过遥测下行的工作参数变化来间接确认命令执行情况，没有标准化的命令执行确认-应答遥测机制。这使得压缩参数变更等关键操作的执行确认缺乏可靠保障。

综上所述，现有卫星测控体系缺乏一种能够利用TC/TM交叉信道实现遥测压缩参数在轨动态协商、上下文同步与故障恢复的标准化方法，这是限制卫星遥测压缩传输工程化应用的关键障碍之一。

## 四、发明/实用新型内容

### 1. 要解决的技术问题

本发明要解决的核心技术问题是：在卫星遥控上行链路与遥测下行链路构成的非对称异步星地交互信道中，如何实现遥测压缩算法参数的可靠双向协商、压缩上下文的持续同步监控，以及上下文失步后的快速恢复。

具体包含以下子问题：

（1）如何设计基于TC上行的压缩协商命令格式，使地面能够向卫星提议压缩算法参数；

（2）如何设计基于TM下行的压缩应答遥测格式，使卫星能够向地面反馈协商结果（含星上处理能力约束）；

（3）如何处理TC命令与TM应答之间的时延不确定性（从数毫秒到数百毫秒），保证协商的正确性；

（4）如何在检测到上下文失步时，利用TC/TM交叉信道快速恢复一致的压缩上下文；

（5）如何支持多地面站并发接入场景下的上下文一致性管理。

### 2. 为解决技术问题而采用的技术方案

**技术方案描述：**

本发明提出一种利用遥控/遥测（TC/TM）交叉信道的卫星遥测压缩参数协商方法（CTCNM，Cross-channel Telemetry Compression Negotiation Method）。该方法通过在TC帧中定义专用压缩控制命令（CCC，Compression Control Command），在TM帧中定义专用压缩状态遥测包（CSTP，Compression Status Telemetry Packet），实现星地之间的双向交互式协商与持续同步监控。

**系统组成与工作原理：**

**（一）协商状态机设计（三阶段握手）**

本发明在卫星星务管理软件中定义压缩协商状态机，包含以下六个状态：

- **UNCOMPRESSED（未压缩态）**：初始状态，遥测以全量非压缩方式传输；
- **NEGOTIATING（协商中）**：已接收COMPRESS_INIT_REQ命令，正在处理；
- **CONFIRMING（等待确认）**：已发出COMPRESS_INIT_ACK遥测，等待地面确认；
- **COMPRESSED（压缩运行态）**：压缩模式正常运行；
- **DEGRADED（降级运行态）**：信道质量下降，自动降低压缩等级；
- **RECOVERING（上下文恢复中）**：检测到上下文失步，正在执行恢复流程。

三阶段握手流程如下：

```
阶段一：初始化请求（地面→卫星）
  地面站通过CCSDS TC帧发送 COMPRESS_INIT_REQ 命令包：
  
  字段          位宽    内容
  ────────────────────────────────────────────────────────
  CMD_TYPE      8 bit   0x43('C') || 0x49('I') → 固定标识
  PROTOCOL_VER  4 bit   请求使用的CTCNM版本号
  ALG_BITMAP    16 bit  地面支持的压缩算法能力位图
                        bit0: PVLC（参数分级压缩）
                        bit1: HDC（头部差分压缩）
                        bit2: PDC（预测差分压缩）
                        bit3-15: 保留
  DICT_VERSION  16 bit  地面使用的参数字典（PLT）版本号
  CTX_WIN_SIZE  8 bit   期望的上下文窗口大小（帧数）
  B_PRECISION   8 bit   B类参数量化精度等级（0-3）
  MAX_RATIO     8 bit   期望最低压缩率（0-100%）
  TIMEOUT_SECS  8 bit   协商超时时间（秒）
  RESERVED      8 bit   保留
  CHECKSUM      16 bit  命令包CRC校验
  总计：12字节
```

```
阶段二：能力应答（卫星→地面，通过TM返回）
  卫星在接收到COMPRESS_INIT_REQ后，评估星上能力，通过专用TM包发送应答：
  
  字段            位宽    内容
  ────────────────────────────────────────────────────────
  PKT_TYPE        8 bit   0x43('C') || 0x41('A') → 固定标识
  RESULT_CODE     8 bit   0x00=接受, 0x01=算法不支持,
                          0x02=字典版本不匹配, 0x03=算力不足,
                          0x04=拒绝（其他原因）
  SELECTED_ALG    4 bit   星上选定的算法ID
  ACTIVE_DICT_VER 16 bit  星上当前使用的PLT版本号
  EFFECTIVE_SEQ   32 bit  压缩生效的TM帧序列号
  MEM_USAGE       16 bit  星上上下文缓存内存占用（字节）
  CPU_OVERHEAD    8 bit   压缩处理CPU占用率（0-100%）
  ACTUAL_RATIO    8 bit   星上预估可达压缩率（0-100%）
  NONCE           32 bit  随机数（用于上下文同步确认）
  CHECKSUM        16 bit  应答包CRC校验
  总计：15字节（封装于CCSDS空间包，APID=0x201）
```

```
阶段三：生效确认（地面→卫星）
  地面收到应答并验证参数后，发送确认命令：
  
  字段            位宽    内容
  ────────────────────────────────────────────────────────
  CMD_TYPE        8 bit   0x43('C') || 0x43('C') → 固定标识
  NONCE_ECHO      32 bit  回显阶段二中的NONCE值（防重放）
  EFFECTIVE_SEQ   32 bit  确认生效的TM帧序列号（与阶段二一致）
  GROUND_TIME     48 bit  地面UTC时间戳（用于时延估算）
  CHECKSUM        16 bit  确认包CRC校验
  总计：16字节
```

卫星收到含正确NONCE的确认命令后，在EFFECTIVE_SEQ指定的帧序号起正式启动压缩模式，状态机从CONFIRMING转入COMPRESSED。

**（二）上下文同步监控机制**

在COMPRESSED状态下，地面接收端持续监控以下两个指标：

（a）**帧序列号连续性**：每收到一个压缩遥测帧，检查帧序列号是否等于上一帧序列号+1。若出现跳变（说明有帧丢失），记录丢失帧数量；

（b）**A级参数哈希一致性**（结合专利1的机制）：当压缩帧携带A级哈希时，与本地缓存比对；

当以下任意条件满足时，地面判定上下文失步：
- 连续丢失帧数 ≥ Nmax（可配置，默认Nmax=3）；
- A级哈希不一致；
- 解压缩输出中出现物理不合理值（如温度值超出传感器量程）。

**（三）上下文失步恢复流程**

当地面检测到上下文失步时，执行以下恢复流程：

```
步骤1：地面发送 COMPRESS_RESYNC_REQ 命令（TC上行）
  字段              位宽    内容
  ────────────────────────────────────────────────────────
  CMD_TYPE          8 bit   0x43('C') || 0x52('R')
  LAST_GOOD_SEQ     32 bit  最后一个成功解压的帧序列号
  RESYNC_MODE       8 bit   0x00=全量上下文快照模式
                            0x01=从指定帧序号回溯模式
                            0x02=最小上下文（仅C级）模式
  CHECKSUM          16 bit  CRC校验

步骤2：卫星收到COMPRESS_RESYNC_REQ后，根据RESYNC_MODE选择响应策略：
  - 0x00模式：连续发送N_snapshot帧（默认N_snapshot=5）全量TM帧（
    不压缩，所有参数携带完整值），重建地面PCC；
  - 0x01模式：从LAST_GOOD_SEQ+1帧起以压缩模式重传（需星上有历史缓存）；
  - 0x02模式：发送1帧全量TM帧（最快恢复，适用于紧急情况）；
  
步骤3：恢复帧以专用APID=0x202传输，地面识别后用于重建PCC，
      恢复完成后APID切换回正常压缩遥测的0x200。
```

**（四）多地面站上下文一致性管理**

在多地面站（如多站联合测控）场景中，每个地面站独立维护自己的压缩上下文（PCC），但共享同一份参数字典（PLT）。当一个地面站触发COMPRESS_RESYNC_REQ时，星上发出的全量恢复帧通过遥测多路广播（Multicast）同时更新所有已授权地面站的PCC。具体机制：

- 每个已授权地面站在与卫星成功完成三阶段握手后，被分配唯一的地面站ID（GS_ID，8位）；
- 卫星维护已授权地面站列表，任意站触发重同步时，卫星在恢复帧TM帧头的辅助字段中附加GS_ID=0xFF（广播标识），指示所有地面站更新PCC；
- 不同地面站的ALG_BITMAP和字典版本差异通过COMPRESS_INIT_REQ的独立协商解决（每站独立协商）。

**（五）压缩参数在线动态更新**

在COMPRESSED状态下，地面可随时发送 COMPRESS_PARAM_UPDATE 命令，动态调整特定参数的压缩等级或量化精度，无需重新完整协商：

```
字段              位宽    内容
──────────────────────────────────────────────────────────
CMD_TYPE          8 bit   0x43('C') || 0x55('U')
PARAM_ID          16 bit  待更新参数的参数ID
NEW_LEVEL         2 bit   新波动等级（0=A, 1=B, 2=C）
NEW_PRECISION     4 bit   B级新量化精度
EFFECTIVE_FRAMES  8 bit   生效帧数（从下一帧起计）
CHECKSUM          16 bit  CRC校验
总计：8字节
```

星上接收后立即更新PLT对应表项，并在下一压缩帧的PLT变更通知字段中告知地面，保证PLT同步。

### 3. 技术方案基础上的改进与变形

**（1）自适应协商触发机制（无需地面指令）**

基础方案需地面主动发起协商。改进方案中，星上增加自主协商触发逻辑：当星上检测到下行信道质量改善（如信噪比从低于门限值恢复正常）时，星上主动通过TM发送COMPRESS_CAPABILITY_ADV（能力通告）包，告知地面当前星上压缩能力，由地面决策是否发起协商。

**（2）NONCE安全增强**

基础方案采用32位随机数NONCE防重放。改进方案中，将NONCE与地面时间戳绑定（使用48位时间戳的低32位作为NONCE种子，经CRC-32变换生成），即使攻击者截获NONCE，也无法在不知道确切时间戳的情况下构造有效重放攻击，提升协商安全性。

**（3）渐进式压缩协商**

改进方案支持分阶段提升压缩等级：首次协商时选择最保守的压缩算法（如仅做头部压缩），运行稳定N帧后，自动发起二次协商，在第一阶段基础上追加参数值压缩，最终实现全功能压缩。此方案降低了协商失败风险，适合新型压缩算法初次部署。

**（4）基于测控弧段的协商时机优化**

考虑到卫星每次过顶弧段持续时间有限（典型LEO卫星8-15分钟），可在弧段开始（信道建立后）立即触发协商，压缩模式在弧段前30秒内完成协商并生效，最大化利用弧段内的压缩增益。改进方案中增加弧段开始事件触发的协商自动化流程。

**（5）协商失败降级策略**

当协商超时或星上返回拒绝应答时，基础方案简单放弃本次协商。改进方案中增加降级协商策略：若ALG_BITMAP不匹配，地面自动缩减至双方共同支持的最小算法集重试；若字典版本不匹配，地面发起PLT字典上行注入流程后重试协商。

### 4. 有益效果

**有益效果：**

（1）**首次实现遥测压缩的星地在轨动态协商**：本发明创造性地利用TC/TM交叉信道构建双向协商信道，填补了CCSDS标准体系中压缩参数动态协商机制的空白，使遥测压缩真正具备工程化在轨部署能力。

（2）**三阶段握手保障协商可靠性**：类比TCP三次握手，三阶段握手机制有效解决了TC/TM异步交互中的时延不确定性问题，通过NONCE防重放机制确保协商过程的唯一性和正确性，避免因命令重传导致协商状态混乱。

（3）**上下文失步快速恢复**：COMPRESS_RESYNC_REQ/恢复帧机制将上下文失步恢复时间从"等待下次整星重启"缩短至"2个遥控/遥测来回时延内"，极大提升了系统鲁棒性，对低轨卫星（单次弧段仅8-15分钟）尤为重要。

（4）**支持多地面站并发管理**：广播恢复机制解决了多站联合测控场景下的上下文一致性难题，为复杂测控网络运营提供了技术支撑。

（5）**参数在线精细调节**：COMPRESS_PARAM_UPDATE命令允许运控人员针对特定参数实时调整压缩策略，满足不同任务阶段对特定参数监测精度的差异化需求（如载荷开机时自动提升相关参数精度）。

（6）**低开销双向协议**：各协商命令包均不超过16字节，在标准CCSDS TC帧（最大248字节用户数据）中具有极低的开销占比，不影响正常遥控命令的传输效率。

## 六、具体实施方式

**具体实施方案如下：**

以某低轨通信卫星首次在轨部署遥测压缩功能为例，详述CTCNM方法的完整实施过程：

**实施场景**：卫星发射后3个月，地面运控人员决定启用遥测压缩，以扩充慢遥参数监测覆盖面。地面站具备PVLC算法解压缩能力（bit0置1），PLT字典版本号为V1.3（0x0013）。

**步骤一：地面站准备**

地面运控软件检查当前与卫星的遥测接收质量，确认当前BER<10^-6（信道质量良好），决定发起压缩协商。构造COMPRESS_INIT_REQ命令：PROTOCOL_VER=1, ALG_BITMAP=0x0001（仅PVLC）, DICT_VERSION=0x0013, CTX_WIN_SIZE=10（10帧上下文窗口）, B_PRECISION=1（中等精度）, MAX_RATIO=70%（期望至少70%压缩率）, TIMEOUT_SECS=30（30秒超时）。

**步骤二：TC命令发送**

地面站将COMPRESS_INIT_REQ封装为CCSDS TC帧（VCID=0, SCID=卫星ID, MAPID=专用MAP），通过S波段上行链路发送。

**步骤三：星上处理**

卫星遥测处理单元接收并解析TC帧，提取COMPRESS_INIT_REQ内容：

- 检查ALG_BITMAP=0x0001，星上支持PVLC（bit0=1），通过；
- 检查DICT_VERSION=0x0013，与星上PLT版本一致，通过；
- 评估当前CPU占用率：PVLC编码预计占用3.2%（<10%阈值），通过；
- 生成NONCE=0xA3F2C891（伪随机数），计算EFFECTIVE_SEQ=当前帧序号+100；
- 构造COMPRESS_INIT_ACK（RESULT_CODE=0x00），封装为CCSDS空间包（APID=0x201）立即发送。

**步骤四：地面确认**

地面接收到COMPRESS_INIT_ACK后：

- 验证RESULT_CODE=0x00，协商接受；
- 记录EFFECTIVE_SEQ和NONCE；
- 构造COMPRESS_CONFIRM（NONCE_ECHO=0xA3F2C891），发送TC命令；
- 同时将本地PCC初始化为当前遥测参数缓存值，准备接收压缩帧。

**步骤五：压缩模式生效**

卫星收到COMPRESS_CONFIRM并验证NONCE后，在第EFFECTIVE_SEQ帧起，遥测处理单元切换为PVLC压缩编码模式，压缩遥测帧通过APID=0x200传输。

**步骤六：模拟上下文失步恢复**

3小时后，卫星进入地球阴影区，信号受遮挡，连续丢失7帧遥测。地面检测到帧序列号跳变（当前帧序列号=N+7，而期望=N+1），判定上下文失步：

- 地面发送COMPRESS_RESYNC_REQ（LAST_GOOD_SEQ=N, RESYNC_MODE=0x00）；
- 卫星切换至RECOVERING状态，连续发送5帧全量TM帧（APID=0x202）；
- 地面接收5帧全量TM帧，重建PCC，所有256个参数恢复为确认值；
- 卫星发送PCC重建完成通知（嵌入普通TM帧辅助字段），地面确认后，卫星恢复COMPRESSED状态，APID切回0x200；
- 整个恢复过程耗时：TC发送至TM应答约2×T_prop（LEO约0.02秒），全量恢复帧5帧约0.5秒，总计<1秒内完成恢复。

## 七、技术创新点概括

本方案重点要保护如下几方面的创新点：

1）**基于TC/TM交叉信道的遥测压缩参数双向协商方法**：利用遥控TC帧携带压缩能力请求、遥测TM帧携带星上能力应答的交叉信道机制，首次实现遥测压缩参数的在轨动态协商，这在CCSDS及现有航天工程实践中均属首创。

2）**三阶段握手协商协议设计**：针对TC/TM异步传输特性设计的三阶段握手流程（REQ→ACK→CONFIRM），通过NONCE机制解决时延不确定性和防重放问题，保障协商可靠性的完整协议设计。

3）**上下文失步检测与快速恢复流程**：基于帧序列号连续性监控和A级哈希验证的失步检测方法，以及通过TC触发、TM全量帧恢复的快速上下文重建机制。

4）**多地面站并发上下文一致性管理方法**：通过广播恢复帧机制实现多地面站场景下的PCC同步，及基于GS_ID的多站并行协商管理方法。

5）**压缩参数在线精细动态调整命令格式**：COMPRESS_PARAM_UPDATE命令及其对应的PLT同步机制，实现单参数级别的压缩策略在线热更新。
